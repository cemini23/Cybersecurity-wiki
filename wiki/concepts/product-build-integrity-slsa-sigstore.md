## Raw Concept

**In scope:** SLSA levels/provenance as architecture; Sigstore keyless signing; reproducible-build criteria; what "verify on update" means; the product ship-bar steal. First-party docs: slsa.dev, docs.sigstore.dev, reproducible-builds.org.

**Out of scope:** bypassing CI integrity; forging provenance/attestations; signing-key exfiltration procedures; CI/CD platform exploitation. No fake SLSA attestations — this is the defender/product side.

## Narrative

### 1. The release-artifact layer vs the dependency layer

Anti-tamper (`@concepts/anti-tamper-protection-classes.md`) and runtime attestation (`@concepts/mobile-app-attestation.md`) protect the running client. But if the **binary you ship is not the binary you built** — a compromised build host, a hijacked CI runner, an insider in the build — no amount of client-side integrity helps. Build integrity is the guarantee that the artifact a consumer receives is the artifact your build system produced, from the source you intended.

The supply-chain layers are complementary, not alternatives:

- **Dependency layer** (`@concepts/npm-supply-chain-defense.md`): what enters the tree — release-age cooldown, version pinning, lockfiles.
- **Release-artifact layer** (this page): what leaves the build — provenance, signatures, reproducibility.

### 2. SLSA — supply-chain levels for software artifacts

SLSA (Supply-chain Levels for Software Artifacts) is a set of increasing supply-chain security guarantees. The **v1.0 spec replaced the old SLSA 1–4 ladder with a build track** at levels L0–L3: [CONFIRMED slsa.dev — @sources/slsa-supply-chain-levels.md]

| Level | Requirement | What it prevents |
|-------|-------------|------------------|
| **L0** | None — "the lack of SLSA" | — |
| **L1** | Provenance exists, describing build platform / process / top-level inputs | Mistakes; provenance may be unsigned and is "trivial to bypass or forge" |
| **L2** | **Signed** provenance generated by a **hosted build platform** | Tampering *after* the build (signature binds the artifact to the platform) |
| **L3** | **Hardened** build platform — runs can't influence one another; signing secrets kept out of user-defined build steps | Tampering *during* the build (insider threats, compromised credentials, other tenants) |

Goal framing: "confidence that software hasn't been tampered with and can be securely traced back to its source." [CONFIRMED slsa.dev]

### 3. Sigstore — keyless signing

Sigstore (OpenSSF / Linux Foundation public-good service) replaces long-lived key management with **identity-based, ephemeral signing**: [CONFIRMED docs.sigstore.dev — @sources/sigstore-overview.md]

- **Cosign** (client): generates an ephemeral keypair, sends a certificate-signing request to Fulcio with a verifiable **OIDC identity token** (email, service account, CI workflow identity).
- **Fulcio** (CA): verifies the OIDC token and issues a **short-lived certificate** binding the identity to the public key. The private key is discarded after a single signing.
- **Rekor** (transparency log): the artifact's digest, signature, and certificate are persisted in an append-only ledger — public audit of signing events.

Verification: check the signature with the cert's public key → confirm the identity matches the expected one → verify the cert chain to Sigstore's root of trust → prove inclusion in Rekor. [CONFIRMED docs.sigstore.dev] The identity shift matters: you verify **who** signed (an OIDC identity), not a manually-exchanged key.

### 4. Reproducible builds — independent verification

Reproducible-builds.org defines the practice as "a set of software development practices that create an independently-verifiable path from source to binary code." Three criteria: [CONFIRMED reproducible-builds.org — @sources/reproducible-builds.md]

1. **Deterministic build** — same source always produces the same result (no timestamps, stable output order).
2. **Recorded or predefined environment** — the build environment and tool set are recorded/defined.
3. **Independent verification** — third parties can recreate a close-enough environment, rebuild, and compare outputs.

The supply-chain payoff: tampering with the build process is detected **early**, and third parties can independently confirm the artifact matches its source ("certainty that software is genuine and has not been tampered with"). [CONFIRMED reproducible-builds.org]

### 5. Product steal — ship and verify

1. **Sign your releases** — Sigstore keyless is the low-friction path (no key management).
2. **Produce and publish provenance** — SLSA L2 minimum: signed provenance from a hosted build platform.
3. **Verify on the update path** — your updater must check the signature/attestation, not just download bytes. An auto-updater that fetches unsigned binaries is a remote-code-execution vector for whoever can serve the host.
4. **Pin builders and keep signing secrets out of user-defined build steps** (L3) for high-value artifacts.
5. **Don't trust "our CI said so" without provenance.** A claim that "the build passed" is not evidence the artifact matches the source; signed provenance is.

### 6. The anti-tamper connection

Client anti-tamper ("don't modify our binary") and build integrity ("the binary we ship is the binary we built") are the two halves of release integrity. `@concepts/anti-tamper-protection-classes.md` handles the running artifact; this page handles the artifact at rest, before it ever reaches the client.
